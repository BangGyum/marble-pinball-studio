# 120Hz 렌더링 지원 보완 — 2026-09-29

경기 화면은 기존의 `requestAnimationFrame`과 위치 보간으로 디스플레이 주사율을 따릅니다. 이번 변경은 고주사율에서 렌더 시간을 확보하도록 물리 처리 예산을 조정하고, 구슬 100개로 60·120·144Hz 동작을 검증한 것입니다. 물리 계산 주기나 충돌 설정을 바꾸지 않았습니다.

## 적용 내용

- `src/game.ts`: 고정 6ms였던 프레임당 물리 처리 예산을 콜백 간격의 36%, 최대 6ms로 조정했습니다. 정상적인 60Hz에서는 6ms, 120Hz에서는 3ms, 144Hz에서는 약 2.5ms입니다. 한 번 시작한 물리 스텝은 중간에 끊지 않으며 최소 한 스텝은 진행합니다. 부하가 크면 기존과 같이 누적 지연을 버리고 경기 진행 속도가 느려질 수 있습니다.
- 기존의 초당 60회 물리 계산과 구슬·장애물 보간, 시간 기반 카메라 이동으로 120Hz 화면에서 중간 위치를 그립니다. 별도 게임 설정 없이 모니터와 브라우저 주사율을 따릅니다.
- 진단 화면에 60/120FPS 목표, 전체 경기 프레임 CPU 처리 시간, 8.33ms 예산 초과 횟수를 추가했습니다. 목표 선택은 표시 주사율을 강제로 바꾸지 않습니다.
- `activeFps`와 `activeFrame`은 경기 종료 뒤 대기를 제외합니다. 기존 FPS·렌더·물리 통계도 그대로 기록합니다. `activeSlowFrames`는 목표 프레임 간격의 1.5배 초과 횟수이며 `workOverBudget`는 전체 경기 프레임 CPU 처리 시간이 목표 예산을 넘은 횟수입니다.
- 대기/일시정지 시 유휴 렌더 절약과 30FPS 녹화는 유지합니다. LAN은 기존 수신 주기에서 보간하며 서버 전송 빈도를 늘리지 않았습니다.

## 자동 검증

`tests/high-refresh.cjs`를 `test:unit`에 추가했습니다.

1. 물리 스텝 3.2ms·렌더 2.2ms를 가정한 과부하 재현: 수정 전 120Hz 콜백에서 물리 두 스텝을 시작해 총 8.6ms를 사용했습니다. 수정 후 한 스텝 뒤 렌더로 넘어가 총 5.4ms로 통과합니다. 이는 제어된 회귀 테스트 수치이며 실제 장치 FPS 측정값은 아닙니다.
2. 실제 Box2D WASM, 고정 시드, 구슬 100개로 분기점·익스프레스·차고지를 각각 60/120/144Hz, 1/4배속으로 진행했습니다. 물리 스텝 수와 100개 구슬의 네이티브 위치·각도가 주사율별로 정확히 일치했습니다. 매 실행은 2초의 콜백 시간이며 테스트용 시계는 처리 비용의 영향을 제거합니다.
3. 경기 중 120/144Hz 콜백마다 렌더하며 중간 물리 위치를 보간합니다. 일시정지·재개와 편집기 복귀는 멈춰 있던 시간을 따라잡지 않습니다.
4. LAN도 100개 구슬, 20Hz 스냅샷에서 120/144Hz마다 그리며 서로 다른 중간 위치를 표시합니다. 기존 LAN 지터·배속·카메라 테스트도 통과했습니다.

최종 검증:

- `npm run test:unit`: 통과.
- `npm run test:lan`: 재생 및 실제 HTTP/WebSocket 테스트 통과.
- `npm run build`, `npm run build:lan`: 프런트엔드·공유 LAN·서버 타입 검사와 빌드 통과.
- 진단 TypeScript 별도 타입 검사 및 진단 페이지 빌드 통과.
- 장시간 맵 완주 묶음은 이번에 재실행하지 않았습니다. 물리 엔진·맵 정의를 변경하지 않고 콜백 처리 예산을 보완했습니다.

## 브라우저 확인과 한계

현재 내장 브라우저의 RAF는 약 60Hz였습니다. 새 진단 화면으로 구슬 100개, 캔버스 1000×600 CSS 픽셀, DPR 1.75, 워밍업 2초와 측정 12초를 확인했습니다. 측정 중 빌드·다른 테스트는 실행하지 않았습니다.

| 조건 | 경기 중 실측 FPS | 경기 프레임 CPU p95 | CPU 8.33ms 초과 |
|---|---:|---:|---:|
| 익스프레스 1배속 | 59.75 | 10.4ms | 76회 |
| 익스프레스 1배속·연속 확대 | 59.58 | 9.5ms | 64회 |
| 익스프레스 4배속 | 59.67 | 11.5ms | 470회 |
| 모래시계 4배속 | 60.00 | 9.4ms | 60회 |

모래시계의 경기 구간은 5.3초였습니다. 전체 측정 12초 중 경기 종료 후 대기를 제외한 통계가 정상 기록됨을 확인했습니다. 콘솔 오류는 관찰되지 않았습니다.

위 CPU 시간은 60Hz 콜백에서 측정한 값으로, 120Hz에서 물리 스텝이 배분되는 방식과 다릅니다. 또한 물리 스텝만의 비용이 아니라 `Race.advance()`와 캔버스 렌더까지 포함하므로 이전 개별 물리/렌더 수치와 같은 지표가 아닙니다. 순위 DOM, 녹화 및 GPU 표시 시간은 포함하지 않습니다.

**120/144Hz 콜백에서의 동작은 자동 검증했지만, 실제 120Hz 디스플레이에서 지속적인 120FPS 표시는 확인하지 못했습니다.** CPU 예산 초과도 관측되어 모든 맵·배속에서 고정 120FPS를 보장하지 않습니다. 실제 지원 환경에서는 `npm run dev:performance`의 진단 목표를 120FPS로 두고 `activeFps`, `activeFrame`, `frameWork`를 함께 확인해야 합니다.

## 재검증

구슬 100개를 실제 Box2D에서 60/120/144Hz 콜백으로 재실행했습니다. 분기점·익스프레스·차고지 각각 1·4배속에서 물리 스텝 수와 최종 구슬 위치·각도가 다시 일치했습니다. LAN 재생·보간, 게임 엔진 회귀, 프런트엔드·LAN·서버 타입 검사도 통과했습니다.

같은 내장 브라우저에서 익스프레스 100개·1배속을 새로 측정한 결과는 **59.42FPS**, 프레임 간격 p95 **17.1ms**, 전체 프레임 CPU 시간 p95 **10.2ms**였습니다. 12초의 경기 구간에서 CPU 8.33ms를 초과한 프레임은 97개였습니다. 브라우저 RAF 자체가 약 60Hz로 관측되므로 이 결과는 실제 120Hz 디스플레이의 FPS가 아닙니다. 이번 재검증도 지속 120FPS 달성을 증명하지 않으며, 목표 환경 실측이 필요합니다.
